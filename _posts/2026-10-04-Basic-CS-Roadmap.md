## 0. Intro

CS를 어떻게 공부해야 하냐는 질문을 수도 없이 받았다.

막상 전부 알려주려고 하면 범위가 매우 넓다. 컴퓨터 구조, OS, 자료구조, 알고리즘, 네트워크, DB 전부 다 CS고, 이걸 처음부터 전부 병행하기엔 시간적으로도 체력적으로도 무리가 있다.

그래서 이 글은 내가 작성한 코드가 컴퓨터에서 어떻게 실행되는지를 이해하기 위한, 최소한의 기초 CS를 공부하는 로드맵이다.

시작하기 전에 C 언어는 어느 정도 공부하고 오는 것을 추천한다. 변수, 함수, 배열, 포인터가 무엇인지 알고 간단한 프로그램을 작성할 수 있는 정도면 된다.

특히 C, C++, Rust처럼 메모리를 직접 신경 써야 하는 언어를 공부할 때 같이 보기 좋은 내용으로 구성했다.

처음부터 두꺼운 책이나 긴 강의를 하나 잡고 전부 공부할 필요는 없다. 아래 섹션을 하나씩 AI한테 복붙해서 처음 배우는 사람 기준으로 설명해달라고 하면 된다. 작은 문제도 같이 요청하는 것을 추천한다.

## 1. 숫자와 메모리

일단 컴퓨터가 숫자나 문자 같은 값을 어떻게 저장하는지부터 알아야 한다.

코드에서는 그냥 `int x = 10`처럼 값을 넣지만, 컴퓨터 안에서는 결국 수많은 `0`과 `1`로 저장된다.

여기서 bit와 byte가 무엇인지부터 시작해서 2진수와 16진수를 보면 된다. 그다음 정수와 실수가 컴퓨터 안에서 어떻게 표현되는지 보면 된다.

같은 정수라도 저장할 공간은 한정되어 있기 때문에 무한히 큰 숫자를 저장할 수는 없다. 음수를 사용하는지에 따라서도 저장할 수 있는 숫자의 범위가 달라진다.

실수는 조금 더 특이하다. 우리가 사용하는 `0.1`, `0.2` 같은 숫자도 컴퓨터에서는 정확하게 표현하지 못하는 경우가 있다. 그래서 `0.1 + 0.2`를 계산했는데 생각했던 것과 조금 다른 값이 나오는 일도 생긴다.

> 왜 타입마다 크기가 다르고 저장할 수 있는 값의 범위도 다른지, 그리고 코드에서 사용하는 값들이 결국 메모리 어딘가에 저장된다는 것까지 이해해야 한다.

## 2. CPU와 Assembly

메모리에 저장된 값을 CPU가 어떻게 가져와 계산하고, 어떻게 다시 저장하는지를 알아야 한다.

우리는 `a + b`처럼 덧셈을 쓰고, `if`로 조건문을 만들고, 함수를 호출한다. 하지만 CPU가 C나 C++ 문법을 그대로 읽고 실행하는 건 아니다.

우리가 작성한 코드는 CPU가 이해할 수 있는 아주 단순한 명령들로 바뀐다. CPU는 그 명령을 하나씩 실행하면서 값을 옮기고, 더하고, 비교하고, 필요한 메모리를 읽는다.

여기서 Register, 명령어, 메모리 접근, 함수 호출 같은 개념을 만나게 된다.

이때 Assembly도 같이 보면 좋다. 그렇다고 Assembly로 직접 프로그램을 작성할 필요는 없고, 우리가 작성한 코드가 CPU 입장에서 어떻게 보이는지 구경하기 위한 도구 정도로 생각하면 된다.

처음에는 `RAX`, `EAX` 같은 레지스터가 무엇인지, `mov`, `add`, `cmp`, `jmp`, `call`, `ret`처럼 자주 보이는 명령이 대충 무슨 일을 하는지만 알면 충분하다. 나머지는 필요할 때 찾아보면 된다.

> 간단한 코드를 보고 컴파일했을 때 CPU가 어떤 일을 해야 할지 대충 생각할 수 있으면 된다.

## 3. 코드와 메모리 연결하기

이제 평소에 작성하던 코드를 실제 메모리와 연결해서 생각해보면 된다.

변수는 실제로 어디에 생길지, 함수 안에서 만든 변수는 함수가 끝난 뒤에도 남아 있을지, Pointer에 들어 있는 주소는 언제까지 사용할 수 있는지 등등.

여기서 Stack과 Heap이라는 메모리 영역을 만나게 된다. Pointer와 Reference가 실제로 무엇을 가리키는지도 조금 더 구체적으로 볼 수 있다.

그리고 메모리에 값이 만들어졌다고 해서 그 값이 프로그램이 끝날 때까지 계속 존재하는 건 아니다. 값이 언제 만들어지고 언제 사라지는지를 나타내는 Lifetime도 같이 보면 된다.

변수가 어디에 만들어지는지, 함수가 끝나면 어떤 값이 사라지는지, 어떤 주소를 알고 있다고 해서 그 메모리를 항상 읽어도 되는지를 생각해보면 된다.

문법만 봤을 때는 귀찮아 보였던 규칙들이 실제로 어떤 문제를 막기 위한 것인지 보이기 시작한다.

실제로 메모리 규칙은 많이 복잡해서 처음부터 깊게 파기보다는 작은 코드에서 값이 언제 만들어지고, 언제 사라지는지 따라가면 된다.

> 값과 주소가 무엇이 다른지, 주소를 알고 있다고 해서 그 메모리를 언제나 사용할 수 있는 건 아닌 이유를 설명할 수 있으면 된다.

## 4. 소스 코드에서 실행 파일까지

지금까지는 이미 실행되고 있는 프로그램 안에서 무슨 일이 일어나는지를 봤다. 그런데 우리가 작성하는 코드는 처음부터 CPU가 실행할 수 있는 형태가 아니다.

이번에는 소스 코드를 작성하고 빌드 버튼을 눌렀을 때, 그 코드가 어떻게 실행 파일이 되는지를 보면 된다.

Compilation과 Linking부터 보고, 둘의 차이가 잡히면 Static Linking과 Dynamic Linking까지 보면 된다.

실행 파일의 내부 구조를 전부 외울 필요는 없다. 코드와 데이터가 있고, 다른 코드와 연결하기 위한 정보도 있다는 정도만 알면 된다.

여기까지 공부했다면 Compiler와 Linker가 서로 다른 일을 한다는 것부터 설명할 수 있으면 된다.

> 코드 문법에는 문제가 없어서 컴파일은 됐는데 왜 그다음 단계에서 에러가 날 수 있는지, 어떤 프로그램은 실행할 때 왜 별도의 라이브러리가 필요한지를 이해하면 된다.


## 5. 운영체제와 프로그램

실행 파일을 실행한다고 해서 프로그램이 혼자 컴퓨터 전체를 마음대로 사용하는 건 아니다. 우리가 평소 사용하는 프로그램 뒤에는 운영체제가 있다.

파일을 읽거나 네트워크를 사용하고, 메모리를 확보하는 일은 프로그램 혼자서 처리할 수 없다. 필요한 작업을 운영체제에 요청해야 한다.

여기서는 System Call, Process, Thread, Virtual Memory, File I/O, 정도를 공부하면 된다.

프로그램에서 사용하는 주소가 곧바로 실제 RAM의 물리 주소를 뜻하는 건 아니라는 것부터 이해하면 된다. 여러 프로그램이 동시에 실행돼도 각 프로그램이 자기만의 메모리를 가진 것처럼 사용할 수 있게 OS가 관리한다는 점도 같이 보면 된다.

처음부터 Page Table, Scheduler까지 들어갈 필요는 없다.

지금은 운영체제를 구현하려는 게 아니라, 내 프로그램이 운영체제 위에서 어떻게 실행되는지를 이해하는 게 목적이다.

> 프로그램이 실행 중인 상태가 무엇인지, 메모리와 파일을 사용하려면 OS가 왜 필요한지를 설명할 수 있어야 한다.

## 6. 여러 작업이 같이 실행될 때

이제 여러 Thread가 동시에 같은 데이터를 다루는 상황을 보면 된다.

무작정 Thread를 여러 개 만든다고 모든 일이 빨라지는 건 아니다. 같은 데이터를 동시에 수정하면 실행 결과가 달라질 수도 있고, 서로를 기다리다가 아무것도 진행할 수 없게 될 수도 있다.

여기서 Race Condition, Mutex, Atomic 같은 개념이 나온다. CPU Cache도 같이 보기 시작하면 성능과 동기화가 복잡한 이유를 알 수 있다.

Memory Ordering이나 Lock-free 자료구조까지 한 번에 들어가는 건 너무 깊다. 작은 공유 변수 하나를 안전하게 다루는 것부터 시작해도 배울 게 많다.

> 공유 데이터를 동시에 다룰 때 어떤 문제가 생기고, 동기화가 왜 필요한지를 이해해야 한다.

## 7. Wrapping Up

목차를 대략적으로 나타내면 아래와 같다.

1. 값은 어떻게 저장될까?
2. CPU는 그 값으로 어떻게 계산할까?
3. 내 코드의 변수와 함수는 메모리에서 어떻게 보일까?
4. 소스 코드는 어떻게 실행 파일이 될까?
5. 실행된 프로그램은 OS와 어떻게 상호작용할까?
6. 여러 작업이 동시에 실행되면 어떤 문제가 생길까?

하나싸기 전부 완벽하게 끝내고 다음으로 넘어갈 필요는 없다. 뒤쪽 내용을 보다가 앞쪽에서 이해가 안 됐던 부분이 풀리기도 한다.

추가로 자료구조와 알고리즘도 별도로 같이 공부해야 하고, 네트워크나 데이터베이스는 만드는 프로그램에 맞춰서 공부하면 된다. 이 로드맵으로 CS 개념이 전부 끝나는 건 아니다.

처음부터 모든 걸 알려고 하면 범위가 너무 넓으니, 일단 내가 쓰는 코드 아래에서 무슨 일이 일어나는지 따라가 보고, 설명하다 막히는 부분을 하나씩 채워 가면 된다.
