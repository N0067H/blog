## 0. Intro

CS를 어떻게 공부해야 하냐는 질문을 받았다. 그런데 막상 설명하려고 하면 어디서부터 말해야 할지 애매하다. 범위가 너무 넓다.

컴퓨터 구조, OS, 자료구조, 알고리즘, 네트워크, DB까지 다 CS다. 이걸 처음부터 전부 파겠다고 하면 시간도 체력도 남아나지 않는다.

일단 내가 쓴 코드가 컴퓨터에서 어떻게 돌아가는지만 따라가 보자. 이번 글은 거기에 필요한 내용을 대충 순서대로 묶은 로드맵이다.

시작 전에 C 언어 기초는 좀 알고 있으면 좋다. 변수, 함수, 배열, 포인터가 뭔지 알고 작은 프로그램을 짤 수 있으면 된다.

C, C++, Rust처럼 메모리를 직접 다뤄야 하는 언어를 공부한다면 더 도움이 될 거다.

두꺼운 책부터 펴 놓고 끝까지 버틸 필요는 없다. 아래 내용을 하나씩 AI에 넣고 처음 배우는 사람 기준으로 설명해 달라고 해도 된다. 설명만 읽으면 금방 까먹으니 작은 문제도 같이 풀어 보는 게 좋다.

## 1. 숫자와 메모리

일단 숫자랑 문자가 컴퓨터 안에 어떻게 들어가는지부터 보자.

코드에서는 그냥 `int x = 10`처럼 값을 넣지만, 컴퓨터 안에서는 결국 수많은 `0`과 `1`로 저장된다.

bit와 byte부터 시작해서 2진수, 16진수로 넘어가면 된다. 그다음은 정수와 실수다. 코드에서는 그냥 숫자인데 저장되는 방식은 다르다.

정수라고 아무 숫자나 넣을 수 있는 건 아니다. 들어갈 자리가 정해져 있으니 한계도 있다. 음수까지 쓸 건지에 따라서도 범위가 달라진다.

실수는 조금 다르다. `0.1`, `0.2`처럼 익숙한 숫자도 컴퓨터에서는 정확히 표현하지 못할 수 있다. 그래서 `0.1 + 0.2`의 결과가 예상과 다르게 나올 때도 있다.

> 타입마다 크기와 저장 가능한 값의 범위가 왜 다른지, 코드에서 쓰는 값이 메모리에 어떻게 저장되는지 설명할 수 있으면 된다.

## 2. CPU와 Assembly

값을 넣었으니 이제 계산을 해야 한다. CPU가 그걸 어떻게 하는지 볼 차례다.

우리는 `a + b`처럼 덧셈을 쓰고, `if`로 조건문을 만들고, 함수를 호출한다. 하지만 CPU가 C나 C++ 문법을 그대로 읽고 실행하지는 않는다.

우리가 작성한 코드는 CPU가 이해할 수 있는 단순한 명령으로 바뀐다. CPU는 명령을 차례로 실행하며 값을 옮기고, 더하고, 비교하고, 메모리에서 데이터를 읽는다.

여기서 Register, 명령어, 메모리 접근, 함수 호출 같은 개념이 나온다.

Assembly를 보면 내가 짠 코드가 CPU에는 어떻게 보이는지 감이 온다. 처음부터 Assembly로 프로그램을 짤 필요까지는 없다.

처음에는 `RAX`, `EAX` 같은 레지스터와 `mov`, `add`, `cmp`, `jmp`, `call`, `ret`이 대충 뭘 하는지만 보자. 명령어를 전부 외우겠다고 덤비면 피곤하다. 나머지는 필요할 때 찾으면 된다.

> 간단한 코드를 보고 컴파일했을 때 CPU가 어떤 일을 해야 할지 대충 생각할 수 있으면 된다.

## 3. 코드와 메모리 연결하기

이제 평소 짜던 코드가 메모리에서는 어떻게 생겼는지 보자.

변수는 어디에 만들어질까? 함수 안에서 만든 변수는 함수가 끝나도 남아 있을까? Pointer가 가리키는 주소는 언제까지 사용할 수 있을까?

이런 질문을 따라가면 Stack과 Heap을 만나게 된다. Pointer와 Reference가 실제로 무엇을 가리키는지도 알 수 있다.

만들었으니 언제 없어지는지도 봐야 한다. 값이 한 번 생겼다고 프로그램이 끝날 때까지 버티는 건 아니다. 이렇게 값이 존재하는 기간을 Lifetime이라고 한다.

변수가 어디에 만들어지는지, 함수가 끝나면 무엇이 사라지는지, 주소만 알면 그 메모리를 읽어도 되는지 따져 보자.

문법만 볼 때는 왜 이렇게 귀찮게 하나 싶었던 규칙도 이유가 조금씩 보인다.

복잡한 규칙을 처음부터 다 외울 필요는 없다. 작은 코드 하나 놓고 값이 언제 생기고 언제 사라지는지만 따라가도 배울 게 많다.

> 값과 주소가 무엇이 다른지, 주소를 알고 있다고 해서 그 메모리를 언제나 사용할 수 있는 건 아닌 이유를 설명할 수 있으면 된다.

## 4. 소스 코드에서 실행 파일까지

지금까지는 실행 중인 프로그램 안에서 일어나는 일을 봤다. 하지만 우리가 작성한 코드는 그대로 CPU에서 실행할 수 없다.

그럼 소스 코드가 실행 파일이 되기까지 중간에 무슨 일이 있는 걸까?

Compilation과 Linking이 뭐가 다른지부터 보자. 그다음은 Static Linking과 Dynamic Linking이다.

실행 파일 구조를 통째로 외울 필요는 없다. 코드랑 데이터가 들어 있고, 다른 코드와 연결할 정보도 들어 있다는 정도부터 잡으면 된다.

Compiler와 Linker가 서로 다른 일을 한다는 점은 설명할 수 있어야 한다.

> 컴파일에는 성공했는데 링크 단계에서 실패할 수 있는 이유는 무엇일까? 실행 파일 옆에 특정 라이브러리가 없으면 실행되지 않는 이유도 설명할 수 있어야 한다.

## 5. 운영체제와 프로그램

실행 파일이 나왔다고 끝은 아니다. 이제 OS 위에서 돌아가야 한다. 프로그램이 컴퓨터 자원을 제멋대로 가져다 쓸 수는 없으니, 중간에서 OS가 일을 맡는다.

파일을 읽거나 네트워크를 사용하고, 메모리를 확보하는 일은 프로그램 혼자서 처리할 수 없다. 필요한 작업을 운영체제에 요청해야 한다.

System Call, Process, Thread, Virtual Memory, File I/O 정도부터 보면 된다.

프로그램에서 사용하는 주소가 실제 RAM의 물리 주소를 그대로 뜻하는 것은 아니다. 여러 프로그램이 동시에 실행돼도 각자 자기만의 메모리를 가진 것처럼 사용할 수 있게 OS가 관리한다.

여기서 바로 Page Table이나 Scheduler까지 파고들면 끝이 없다. 일단은 넘어가도 된다.

지금은 OS를 직접 만들려는 게 아니니, 내 프로그램이 그 위에서 어떻게 돌아가는지부터 잡자.

> 프로그램이 실행 중인 상태가 무엇인지, 메모리와 파일을 사용하려면 OS가 왜 필요한지를 설명할 수 있으면 된다.

## 6. 여러 작업이 동시에 실행될 때

하나씩 돌릴 때는 괜찮았는데, 여러 Thread가 같은 데이터를 건드리면 얘기가 좀 달라진다.

Thread를 잔뜩 만든다고 무조건 빨라지지는 않는다. 같은 데이터를 동시에 고치다가 결과가 뒤죽박죽될 수도 있고, 서로 기다리다가 둘 다 멈춰 버릴 수도 있다.

여기서 Race Condition, Mutex, Atomic 같은 개념이 나온다. CPU Cache를 알아두면 성능과 동기화가 복잡한 이유도 더 잘 보인다.

Memory Ordering이나 Lock-free 자료구조까지 한꺼번에 잡으려 하지는 말자. 공유 변수 하나 안전하게 다루는 것도 막상 해 보면 만만하지 않다.

> 공유 데이터를 동시에 다룰 때 어떤 문제가 생기고, 동기화가 왜 필요한지를 이해해야 한다.

## 7. Wrapping Up

대충 훑고 나서 아래 질문에 자기 말로 답해 보면 된다. 설명하다 막히면 거기가 다시 볼 부분이다.

1. 값은 어떻게 저장될까?
2. CPU는 그 값으로 어떻게 계산할까?
3. 내 코드의 변수와 함수는 메모리에서 어떻게 보일까?
4. 소스 코드는 어떻게 실행 파일이 될까?
5. 실행된 프로그램은 OS와 어떻게 상호작용할까?
6. 여러 작업이 동시에 실행되면 어떤 문제가 생길까?

하나 완벽하게 끝내고 다음으로 넘어가겠다고 하면 잘 안 넘어가게 된다. 뒤쪽을 보다가 앞에서 막혔던 게 풀리기도 하니, 좀 헷갈려도 일단 가 보자.

물론 이걸로 CS를 다 봤다는 얘기는 아니다. 자료구조와 알고리즘은 따로 해야 하고, 네트워크나 DB도 만드는 프로그램에 맞춰 배워야 한다.

처음부터 전부 알려고 하면 끝이 없다. 일단 내가 쓰는 코드 밑에서 무슨 일이 벌어지는지부터 따라가면 된다. 모르는 게 나오면 하나씩 채우고. 그것만 해도 공부할 건 많다.
