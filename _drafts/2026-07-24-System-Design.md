## 1. System Design

시스템 디자인은 단순히 서버, 데이터베이스, 캐시를 그림으로 배치하는 작업이 아니다.

- 시스템이 무엇을 해야 하는가
- 얼마나 많은 사용자를 감당해야 하는가
- 어느 정도의 장애까지 허용할 것인가
- 데이터는 얼마나 정확해야 하는가
- 응답은 얼마나 빨라야 하는가
- 개발과 운영에 얼마를 쓸 수 있는가
- 요구사항이 바뀌면 얼마나 쉽게 수정할 수 있는가

시스템 디자인은 이러한 조건 사이에서 무엇을 얻고 무엇을 포기할지 결정하는 과정이다.

작은 서비스라면 아래 정도도 충분한 시스템 디자인이다.

```
- 사용자는 최대 100명 정도
- 요청량이 적으므로 서버 한 대
- 데이터 유실은 허용하지 않으므로 PostgreSQL 사용
- 이미지 파일은 DB가 아닌 오브젝트 스토리지에 저장
- 서버 장애 시 수동 복구 허용
```

시스템 디자인은 거창한 아키텍처 그림일 필요는 없다. 핵심은 어떤 기술을 사용했는지가 아니라, 왜 선택했는지를 설명할 수 있는가다.

## 2. 요구사항 분석

시스템 디자인에서는 가장 먼저 요구사항을 분석해야 한다.

### 2.1. 기능적 요구사항 (Functional Requirements)

시스템이 제공해야 하는 기능을 말한다.

예를 들어, URL 단축 서비스에서는 다음과 같다.

- 긴 URL을 짧은 URL로 변환
- 짧은 URL로 접속하면 원래 주소로 이동
- 사용자는 링크를 삭제할 수 있음
- 클릭 수를 확인할 수 있음

### 2.2. 비기능적 요구사항 (Non-Functional Requirements)

시스템이 기능을 어떤 품질로 제공해야 하는지에 대한 요구사항이다.

- 초당 요청 수
- 응답 시간
- 가용성
- 데이터 정합성
- 확장성
- 유지보수성
- 비용
- 보안
- 내구성

로그인 기능을 제공하는 것은 기능적 요구사항이다. 반면 로그인 요청의 99%를 200ms 안에 처리한다는 조건은 비기능적 요구사항이며, 이러한 조건을 정의하는 것이 시스템 디자인의 시작이다.

## 3. 시스템 디자인의 기본 진행 순서

### 3.1. 요구사항과 범위 정의

가장 먼저 개발 범위를 정해야 한다. 무엇을 만들지와 무엇을 만들지 않을지를 정한다.

예를 들어, 채팅 시스템을 설계한다면 다음과 같다.

```
포함해야 하는 것
- 1:1 메시지
- 메시지 저장
- 온라인 상태

제외해야 하는 것
- 단체 채팅
- 파일 전송
- 종단 간 암호화
```

범위를 정하지 않으면 설계는 끝도 없이 커진다. MVP를 따로 정하는 이유는 다 있다.

### 3.2. 규모 추정

시스템이 사용되는 규모를 추정해야 한다. 정확한 예측이 목적은 아니다. 설계 방향을 결정할 수 있을 정도의 근사치를 구하는 과정이다.

- 일일 활성 사용자 수
- 사용자당 요청 횟수
- 초당 평균 요청 수
- 예상 저장 공간
- 하루 데이터 증가량

예를 들면 다음과 같다.

```
일일 활성 사용자 100만 명
사용자당 하루 20개 요청

하루 요청:
1,000,000 × 20 = 20,000,000

평균 초당 요청:
20,000,000 ÷ 86,400 ≈ 231 RPS

피크 트래픽을 평균의 5배로 가정:
약 1,155 RPS
```

### 3.3. 데이터 모델 설계

데이터를 어떻게 저장하고 조회할지 결정하는 과정이다. 주로 다음 사항을 정리한다.

- 어떤 데이터를 저장하는가
- 데이터 사이의 관계는 무엇인가
- 어떤 조건으로 조회하는가
- 얼마나 자주 읽고 쓰는가
- 트랜잭션으로 처리해야 하는가
- 데이터 삭제와 보존 정책은 무엇인가

DB를 먼저 선택하기보다 접근 패턴을 먼저 정의해야 한다.

나쁜 접근:

```
MongoDB를 요즘 많이 쓰던데 나도 따라 써야지.
```

좋은 접근:

```
메시지를 채팅방과 생성 시간 기준으로 순차 조회해야 한다.
쓰기 작업이 많고, 오래된 데이터는 거의 수정되지 않는다.
이 접근 패턴에 맞는 저장 방식은 무엇일까?
```

### 3.4. 주요 컴포넌트 구성

기본적으로 아래 요소를 검토한다.

```
Client -> Load Balancer -> Server
                              ㄴ Cache
                              ㄴ DB
                              ㄴ Queue
                              ㄴ Object Storage
```

각 컴포넌트는 있어 보여서가 아니라, 구체적인 문제를 해결하기 위해 넣어야 한다.

- 로드 밸런서: 요청 분산과 인스턴스 장애 대응
- 캐시: 반복 조회 비용과 응답 시간 감소
- 메시지 큐: 비동기 처리와 처리량 차이 흡수
- 오브젝트 스토리지: 대용량 파일 저장

### 3.5. 병목과 장애 시나리오

정상적으로 동작하는지뿐만 아니라, 무엇이 실패할 수 있는지도 살펴봐야 한다.

- 서버가 갑자기 죽는 경우
- DB 연결이 고갈되는 경우
- 캐시가 한꺼번에 비워지는 경우
- 메시지 큐 소비자가 멈추는 경우
- 외부 API가 느려지는 경우
- 같은 요청이 두 번 전달되는 경우
- 네트워크가 끊긴 뒤 재연결하는 경우
- 트래픽이 갑자기 10배로 급등하는 경우

AWS 공식 문서를 보면 분산 시스템의 구성 요소보다, 구성 요소 사이에서 발생하는 장애를 완화하거나 견디는 방법을 주로 다루는 경우가 많다.

## 4. 시스템 디자인을 고려하지 않을 때 생기는 문제

이 부분은 내가 직접 경험한 문제를 중심으로 정리했다.

### 4.1. 단일 장애 지점(SPOF)이 생긴다

```
원인:
모든 요청과 데이터를 하나의 서버에 의존한다.

증상:
서버 하나가 죽자 전체 서비스가 중단된다.

결과:
작은 장애가 전체 장애로 확대된다.
```

단일 서버 자체가 무조건 나쁜 것은 아니다. 문제는 단일 장애 지점이라는 사실을 인식하지 못하거나, 장애가 발생했을 때의 복구 전략이 없는 것이다.

### 4.2. 트래픽 증가에 대응하지 못한다

단순 테스트에서는 잘 작동했지만, 동시 사용자가 100명 정도만 넘어가도 다음 문제가 발생했다.

- CPU 사용률 급증
- DB 커넥션 고갈
- 타임아웃 증가
- 메모리 부족
- 특정 쿼리로 인한 DB 부하

특히 평균 트래픽만 생각하고 피크 트래픽을 고려하지 않으면 출시 당일에 장애가 발생하기 쉽다.

### 4.3. 데이터 정합성이 깨진다

결제 시스템에서 다음 순서로 처리한다고 해보자.

```
결제 요청 -> 잔액 차감 -> 주문 생성 -> 응답
```

이때 잔액 차감이 끝난 뒤 서버에 장애가 발생하면, 잔액은 차감됐지만 주문은 생성되지 않은 상태가 된다.

이런 실패 시나리오를 고려하지 않으면 다음 개념도 설계에서 빠지기 쉽다.

- 트랜잭션
- 멱등성
- 재시도 정책
- 보상 트랜잭션
- 중복 메시지 처리
- 이벤트 순서 보장

### 4.4. 재시도가 장애를 더 크게 만든다

요청이 실패했을 때 무조건 즉시 재시도하면, 이미 느려진 서버에 더 많은 요청이 쌓인다.

```
1. 서버 지연
2. 클라이언트 타임아웃
3. 다수의 클라이언트가 즉시 재시도
4. 요청량 증가
5. 서버가 더 느려짐
6. 결국 전체 장애
```

따라서 적절한 타임아웃, 지수 백오프, 재시도 횟수 제한 같은 정책을 함께 고려해야 한다.

### 4.5. 무조건적인 캐시는 좋지 않다

캐시는 단순히 성능을 높여주는 도구가 아니다.

설계 없이 무작정 도입하면 다음 문제가 발생할 수 있다.

- DB와 캐시의 데이터 불일치
- 갱신 이전의 데이터가 사용자에게 노출됨
- 특정 키가 만료될 때 요청 폭주
- 존재하지 않는 데이터에 대한 반복 조회
- 캐시 장애가 전체 서비스 장애로 전파됨

캐시를 넣을 때는 최소한 다음 기준을 정리해야 한다.

```
- 무엇을 캐싱하는가
- 언제 무효화하는가
- TTL은 얼마인가
- 캐시 미스 시 어디서 읽는가
- 캐시가 죽어도 시스템이 동작하는가
```

### 4.6. 기술 선택의 이유가 사라진다

```
Kafka를 왜 사용했나요?
ㄴ 대용량 시스템에서 많이 사용하니까요.

Redis를 왜 사용했나요?
ㄴ 캐시에는 보통 Redis를 사용하니까요.

왜 마이크로서비스를 선택했나요?
ㄴ 확장성이 좋다고 해서요.
```

이 경우에는 문제 해결이 아니라 기술 도입 자체가 목적이 된 것이다.

좋은 시스템 설계는 아래와 같은 과정이 남아야 한다.

```
문제:
주문 요청과 이메일 발송 처리 속도의 차이가 크다.

선택:
주문 이벤트를 메시지 브로커로 전달한다.

효과:
이메일 서버의 지연이 주문 응답 시간에 직접 영향을 주지 않는다.

비용:
운영해야 할 컴포넌트가 늘어나고, 메시지 중복 처리도 고려해야 한다.
```

## 5. 상세한 시스템 디자인 없이 시작해도 되는 경우

완전히 설계 없이 시작한다는 뜻은 아니다. 상세한 선행 설계 대신 최소한의 가정만 세우고 시작하는 경우에 가깝다.

### 5.1. 요구사항이 아직 검증되지 않은 프로토타입

사용자가 이 기능을 원하는지조차 모르는 상황이라면, 확장 가능한 인프라보다 실제 사용 여부를 확인하는 것이 먼저다.

- 해커톤
- 개인 사이드 프로젝트
- PoC

### 5.2. 일회성 프로그램

- 마이그레이션 스크립트
- 한 번 실행할 자동화 도구
- 임시 통계 추출
- 특정 이벤트용 페이지
- 작은 CLI 도구

장기간 운영하지 않는 프로그램에 고가용성, 자동 확장, 복잡한 분산 구조를 넣는 것은 비용 대비 효과가 낮다.

### 5.3. 학습이 목적인 프로젝트

학습 프로젝트에서는 실제 운영에 가장 적합한 선택보다 배우고 싶은 기술을 사용하는 것도 합리적이다.

- 분산 합의를 배우기 위한 간단한 Raft 구현
- 네트워크를 배우기 위한 직접 HTTP 서버 구현
- Kafka를 배우기 위한 이벤트 기반 프로젝트

학습을 위한 기술 선택은 잘못된 선택이 아니지만, 실제 서비스에 적합한 설계라고 일반화하면 안 된다.

### 5.4. 빠른 피드백이 설계보다 중요한 경우

요구사항이 빠르게 바뀌는 초기 제품에서는 설계를 오래 할수록 틀린 가정을 정교하게 만들 위험이 있다.

애자일 선언문 역시 포괄적인 문서보다 동작하는 소프트웨어를, 계획을 따르는 것보다 변화에 대응하는 것을 더 가치 있게 본다.

## 6. 현실적인 시스템 디자인의 기준

작은 프로젝트라도 다음은 적어두는 것이 좋다.

1. 누가 사용하는가
2. 핵심 기능은 무엇인가
3. 예상 사용자와 트래픽은 얼마인가
4. 어떤 데이터를 저장하는가
5. 데이터 유실과 서비스 중단을 얼마나 허용하는가
6. 가장 먼저 병목이 될 부분은 어디인가
7. 장애가 발생하면 어떻게 복구하는가
8. 이 설계에서 의도적으로 포기한 것은 무엇인가

## 7. 결론

시스템 디자인은 복잡한 기술을 많이 사용하는 일이 아니다. 요구사항과 규모를 파악하고, 시스템이 실패할 수 있는 지점을 예상하며, 각 선택의 이유와 비용을 설명하는 과정이다.

모든 프로젝트에 고가용성, 분산 처리, 자동 확장이 필요한 것은 아니다. 작은 서비스는 단일 서버로 시작해도 충분하고, 빠른 검증이 중요한 프로젝트에서는 상세한 설계보다 구현과 피드백이 우선일 수 있다.

중요한 것은 정답처럼 보이는 구조를 만드는 것이 아니라, 현재의 요구사항과 제약에 맞는 선택을 하는 것이다. 그리고 트래픽 증가, 장애, 데이터 정합성, 운영 비용처럼 이후 발생할 수 있는 문제를 미리 생각해야 한다.

결국 좋은 시스템 디자인은 가장 복잡한 설계가 아니라, 무엇을 얻고 무엇을 포기했는지 명확하게 설명할 수 있는 설계다.
